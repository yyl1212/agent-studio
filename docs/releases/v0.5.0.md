# Agent Studio v0.5.0

`v0.5.0` 的目标是面向源码使用者、工作流作者、节点包开发者和运维人员提供正式开发者预览。它仍以本地和隔离环境验证为主，不是生产稳定版，不提供 v1 兼容承诺，也没有生产 SLA。

## 版本与发布边界

本页在标签和 Release 创建前作为发布准备说明；下文安装与附件命令只在 `v0.5.0` 标签工作流成功、远端 9 件附件齐全后适用。执行前请先核对标签、制品及校验和，不要根据本文推断远端当前状态。

| 项目 | 值 |
| --- | --- |
| Runtime 源码开发构建 | `0.5.0-dev` |
| 正式标签 | `v0.5.0` |
| Go Node SDK | `0.5.0` |
| Node API | `agent-studio.dev/v1alpha1` |
| 官方 manifest Runtime 范围 | `[v0.2.0, v0.6.0)` |
| 备份格式 | `agent-studio.dev/backup/v1alpha2`，继续导入受支持的 `v1alpha1` |
| 数据库 | migration 7 |

## 本版范围

- **v0.5-A 可观测性**：Worker 提供队列深度、最老排队时间和采样结果，帮助定位领取、租约和排队问题。
- **v0.5-B 画布体验**：Studio 提供节点配置、草稿保护、版本比较和运行入口。本次收口又为节点预览加入可聚焦的“确认放置 / 取消”操作；配置面板区分本地草稿与整个工作流的保存状态，不把“已应用到画布”误作已持久化。
- **v0.5-C 备份恢复**：备份采用 `v1alpha2`，继续接受受支持的 `v1alpha1` 归档导入；恢复前必须核对实例状态与密钥。
- **v0.5-D 持久运行**：API 将运行写入 PostgreSQL 队列，独立 Worker 领取并执行；无法确认外部副作用的运行进入人工恢复。

## 安装与 9 件附件核验

标签工作流成功后，可按精确版本安装 CLI，并检查显示的模块版本、SDK 与 Node API：

```bash
CGO_ENABLED=0 go install github.com/yyl1212/agent-studio/cmd/agent-studio@v0.5.0
agent-studio version
```

同一工作流应提供四个 archive（`darwin_amd64`、`darwin_arm64`、`linux_amd64`、`linux_arm64`）、各自对应的 SPDX JSON SBOM 和 `checksums.txt`，合计 9 件附件。下载后先校验 checksum，再解压运行：

```bash
VERSION=v0.5.0
OS=darwin
ARCH=arm64
ARCHIVE="agent-studio_${VERSION}_${OS}_${ARCH}.tar.gz"
BASE_URL="https://github.com/yyl1212/agent-studio/releases/download/${VERSION}"

curl -fLO "${BASE_URL}/${ARCHIVE}"
curl -fLO "${BASE_URL}/${ARCHIVE}.spdx.json"
curl -fLO "${BASE_URL}/checksums.txt"
grep "  ${ARCHIVE}$" checksums.txt | shasum -a 256 -c -
tar -xzf "${ARCHIVE}"
./agent-studio version
```

Linux 的校验命令改为 `grep "  ${ARCHIVE}$" checksums.txt | sha256sum -c -`。若已将完整 9 件附件放入 `./release-assets`，可在同版本源码检出中运行 `sh scripts/check-release-artifacts.sh collection ./release-assets "$VERSION"`。校验和只能证明下载内容与附件一致；本版无签名/公证，macOS 制品也没有 Apple Developer ID 签名或公证。

## 部署、容量与升级回滚

在维护窗口内先停止旧 API、旧 Worker 和写库工具，创建并检验升级前备份，再执行 migration 7。将同版本 API 与 Worker 部署到同一数据库，并配置相同密钥 `RUN_PAYLOAD_ENCRYPTION_KEY`；禁止旧/新进程或不同密钥的进程混跑。具体队列检查、legacy 活动运行处理与故障步骤见 [v0.5-D 升级与回滚](../upgrades/v0.5-d.md)。

轻量容量基线为 1 API、1 Worker（concurrency 4）、500 Mock runs，单次演练限制为 10 分钟。它是隔离非生产环境中的可重复验证，不是 SLA，也不承诺生产吞吐或排队时延。先确认 Docker、Compose、curl、jq、Ruby 和 Go 可用，并生成专用测试密钥，不使用真实业务密钥：

```bash
export RUN_PAYLOAD_ENCRYPTION_KEY="$(openssl rand -base64 32)"
make test-rc-capacity-e2e
```

错误密钥会使受影响运行进入人工恢复，不能靠静默重试绕过。需要整库回滚时，停止所有新进程，将升级前备份恢复到经批准的第二个空目标数据库，使用与备份匹配的旧制品和旧配置验证后再恢复流量。禁止 migration 7 逆迁移，禁止让旧二进制连接已升级的数据库，也禁止新旧 API/Worker 混跑；升级后新增运行不会自动写回升级前备份。

## 已知限制

- 单租户、本地优先；不提供登录、RBAC、多租户管理或审计后台。
- 无容器制品、Windows 制品或安装器；预编译 CLI 仅覆盖上述四个平台与架构组合。
- 无本地 RAG、Embedding 或向量数据库闭环。
- 无自动业务重试；外部副作用结果不确定时必须由人员确认恢复或终止。
- 无签名/公证；校验和不能证明发布者身份。

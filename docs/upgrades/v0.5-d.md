# v0.5-D 耐久运行升级与回滚

本手册用于从 migration 6 及更早的 v0.4/v0.5-C 运行方式升级到 migration 7 的 PostgreSQL 队列与独立 Worker。升级需要维护窗口。v0.5-D 不支持旧 API、新 API 或新 Worker 混合运行；所有进程必须来自同一提交或同一镜像摘要。RC 的身份、制品核验和已知限制见 [v0.5.0-rc.1 RC 说明](../releases/v0.5.0-rc.1.md)。

## 版本矩阵

| 组件 | 升级时必须使用的值 |
| --- | --- |
| RC 目标 | `v0.5.0-rc.1` |
| Runtime 源码开发构建 | `0.5.0-dev` |
| Go Node SDK | `0.5.0` |
| Node API | `agent-studio.dev/v1alpha1` |
| 数据库 | migration 7 |
| 备份 | `agent-studio.dev/backup/v1alpha2`，继续接受 `v1alpha1` 导入 |

API 与 Worker 必须同版本、使用同一数据库和相同 `RUN_PAYLOAD_ENCRYPTION_KEY`。版本矩阵不表示允许把旧/新进程同时接入同一实例；升级只在固定维护窗口中进行。

## 升级前检查

- 记录当前受测版本、镜像摘要、数据库地址和配置来源；确认具备回滚所需的旧制品。
- 通知用户暂停提交；记录仍处于 `running` 或 `cancelling` 的运行。
- 准备 Base64 编码的 32 字节随机 `RUN_PAYLOAD_ENCRYPTION_KEY`，通过平台 Secret 保存。不要把值写入命令历史、文档、数据库或 `.asbak`。
- 验证磁盘、PostgreSQL 健康和备份目录权限，并预留完整回归时间。

## 固定维护窗口

严格按以下顺序执行：

1. 停止全部旧 API、旧 Worker、在线备份任务和直接写库工具，确认没有旧进程继续写入。
2. 使用旧版本支持的 v0.5-C 备份流程创建并 `inspect` 备份，保存 `.asbak`、摘要和当时的配置。不要先迁移再冒充升级前备份。
3. 在部署平台配置并校验 `RUN_PAYLOAD_ENCRYPTION_KEY`。API 与 Worker 必须使用相同密钥；缺失或格式错误时应保持启动失败。
4. 部署同版本 API 与 Worker。启动阶段由共享 maintenance lock 串行执行 migration 7；不要并行手工运行 SQL，也不要绕过锁。
5. 等待 API `/readyz` 成功，并确认 Worker 已启动且数据库连接正常。任一进程未就绪时不要恢复流量。
6. 检查 Worker 的队列深度、最老排队时间、领取、活动 lease 和续租指标；确认没有持续的 claim 错误或 fencing 拒绝。
7. 打开管理端“运行”页处理遗留活动运行。migration 7 会把旧 `running` 转为 `recovery_required/legacy_active_run`，旧 `cancelling` 保留取消意图，终态不变。旧运行没有可验证的密文检查点，不允许原地续跑；终止后按需要重新提交。
8. 完成一次 Mock 工作流、取消、Worker 重启接管和备份检查后再恢复用户流量。

禁止旧 API 与新 Worker、不同版本 API/Worker、不同密钥进程混跑。混跑会破坏事件协议和恢复判断，readiness 成功也不能证明组合兼容。

## 升级后核验

```bash
curl -fsS http://127.0.0.1:8080/readyz
docker compose ps
docker compose logs --tail=200 api
docker compose logs --tail=200 worker
```

确认新运行按 `queued → running → terminal/recovery_required` 演进；浏览器或 API 断开后 Worker 仍继续；管理端可处理人工恢复。日志、响应和 telemetry 不应包含密钥、密文、原始输入输出或 lease owner。

## 自动升级与回滚演练

仓库提供以下本地演练命令；运行前必须在环境中配置专用的非生产 `RUN_PAYLOAD_ENCRYPTION_KEY`，且 Docker 可用：

```bash
make test-v05-upgrade-rollback-e2e
```

该命令的自动演练总上限为 10 分钟；不要在生产实例或含业务数据的数据库执行它。

演练只信任仓库内 annotated `v0.4.0` Tag，并校验 Tag 剥离对象确为 commit。脚本把 Tag 源码归档到权限为 `0700` 的临时目录，以 `CGO_ENABLED=0` 构建旧 API；随后在唯一的 PostgreSQL 18 Compose project 中完成 migration 6 夹具、migration 7 升级、当前 API/Worker 冒烟以及恢复验证。命令外层总上限为 10 分钟，内部默认硬上限为 570 秒，另保留最多 20 秒用于收集 PostgreSQL 日志并清理精确的 Compose project；失败 artifact 只允许通过统一敏感信息扫描的日志和安全摘要，不包含升级前 dump 或业务正文。

回滚验证使用第二个独立空库 `rollback_target`：把旧 API 停止后生成的 migration 6 custom dump 恢复到该库，再由同一个 `v0.4.0` 二进制执行 readiness 和旧记录读取。`upgrade_source` 与 `rollback_target` 始终是不同数据库；升级后旧二进制不会重新连接 `upgrade_source`。

## 故障处理

- migration 7 失败：保持所有业务进程停止，保留安全错误信息，排查数据库权限、schema 与 maintenance lock；不要手工标记迁移成功。
- Worker 无法解密：立即停止 Worker，核对 Secret 来源。错误密钥会使运行进入 `recovery_required/payload_unavailable`，不会静默执行。
- 队列不消费：检查 Worker 版本、数据库、claim/lease 指标和配置范围；不要直接改写 `runs`、事件序号或 fencing token。
- 副作用节点等待人工恢复：先到外部系统核对首次尝试结果，再决定确认重试或终止；禁止自动批量重试。

## 回滚

migration 只向前执行，不支持原地逆迁移。需要回滚时：

1. 再次停止并确认全部新 API/Worker 和写库工具已退出，保存故障证据。
2. 不要让旧二进制连接 migration 7 数据库，也不要删除新表或手工降低 migration 版本。
3. 新建或清空经批准的目标 PostgreSQL 实例，恢复升级前验证过的数据库 dump、旧配置和旧版本制品。备份 v1alpha2 虽继续接受 v1alpha1 导入，但数据库回滚仍必须使用升级前 dump。
4. 启动与该备份匹配的旧 API，执行旧版本 readiness 与业务冒烟验证后再恢复流量。
5. v0.5-D 升级后产生的新运行不会回写到升级前备份；明确记录数据时间点并按组织流程处置。

如果问题只影响单个运行，优先使用管理端人工恢复或终止，不要把整库回滚当作运行重试机制。

上述第二空库恢复是唯一受支持的自动回滚演练语义。仍然不支持让旧二进制连接 migration 7 数据库，也不支持删除新表、降低 `schema_migrations` 版本或执行任何 migration 7 逆迁移。
